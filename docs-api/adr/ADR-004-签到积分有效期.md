# ADR-004: 签到积分有效期（过期积分批次台账）

## 状态

Accepted

## 日期

2026-09-17

## 背景（Context）

当前积分是单一余额模型：

- `user_credit_accounts.credit_balance` 是一个整数，前端右上角、积分页、管理端用户列表都直接读它；
- 所有发放（新用户初始积分、邀请奖励、卡密兑换、每日签到、任务退款、管理员增加）都直接累加，所有消耗（图片/视频任务扣费、分镜等同步业务扣费、管理员扣减）都直接扣减；
- `user_credit_transactions` 只记录每次变动金额与余额快照，没有"某笔发放还剩多少"的概念。

签到期引入"签到积分只当天有效"的语义。目前全仓没有任何积分失效能力（只有 `email_verification_codes` 与 `password_reset_tokens` 带 `expires_at`），签到页与后台 Tab 上的"今日有效"只是文案，实际不生效。

需求口径（2026-09-17 确认）：

- **只有签到发放的积分带有效期**；充值、卡密兑换、邀请奖励、新用户初始积分、任务退款、管理员增加的积分都是永久有效；
- 任务失败/取消的退款按新批次发放（不精确回滚到被扣的批次）；
- 前端只在积分明细里体现过期记录，不做"即将过期"提醒。

## 问题（Problem）

让签到积分在有效期结束后自动作废未使用的部分，并且：

- 不改动余额读取路径（多个页面与用户列表都直接读 `credit_balance`）；
- 用户当天消耗积分时，必须**先消耗最快到期的额度**，避免长期积分把短期签到积分挤掉；
- 现有扣费、退款、管理员调整、卡密兑换链路不能出现余额与台账不一致；
- 不改动永久积分的语义，也不需要为永久积分维护闲置的台账。

## 决策（Decision）

采用**只对"会过期的发放"建批次台账 + 先到期先扣（FIFO）**：

- **余额模型不变**：`user_credit_accounts.credit_balance` 仍是用户可见总余额与权威读值；`user_credit_grants` 只记录**会过期**的发放批次，因此恒有 `SUM(remaining_amount) <= credit_balance`。
- **只有每日签到发放写批次**：`source_type = 'daily_check_in'`，`expires_at = 签到时刻 + 24 小时`（`Asia/Shanghai`），即签到后满 24 小时作废。
- **扣减走新原语 `consumeCredits(userId, amount)`**：先在**同一事务**内对该用户做一次惰性过期（把已到期的批次清零、扣减余额、写 `credit_expired` 流水），再按 `expires_at ASC, id ASC` 加行锁（`FOR UPDATE`）扣减批次剩余额度，不足部分再扣账户余额；余额守门仍是 `credit_balance - amount >= 0`。
  - 惰性过期是必须的：有效期不再对齐午夜，如果只靠定时任务，会出现「余额显示有、实际扣不动」的矛盾状态（用户看到 20 分却提示积分不足）。
- **过期由定时任务兜底**：新增 `CreditExpiryScheduler`，**每小时第 5 分钟**（`0 5 * * * *`）对所有存在已过期批次的用户执行一次过期清理，保证展示余额最多滞后 1 小时。沿用项目已有的 `@Scheduled` 模式（`NovanovaStudioServerApplication` 已开启 `@EnableScheduling`，参考 `ApiLogRetentionScheduler`）。
- **退款不写批次**：`task_refund` 直接累加余额，等价于"发一个永久批次"，天然满足"退款发新批次、不精确回滚"。
- **一致性纪律**：批次变更、余额变更、流水写入必须在同一事务内完成；批次扣减保留 `remaining_amount >= take` 守门，余额保留 `credit_balance >= 0` 守门，任一侧不满足即整笔回滚。现有调用点已经满足事务要求（`AiTaskService` 创建任务、`finishTaskWithRefund`、`CreditService.chargeOperation` / `adjustUserCredits` 都包在 `transactionalOperator` 中）。
- **不需要历史数据回填**：`credit_balance` 保持原值，`user_credit_grants` 从空表开始，升级后余额与可用额度不变。

## 表结构

```sql
CREATE TABLE user_credit_grants (
    id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id          BIGINT NOT NULL REFERENCES users(id),
    source_type      VARCHAR(30) NOT NULL,   -- 目前只有 daily_check_in
    source_ref       VARCHAR(64),            -- 签到记录ID，便于追溯
    granted_amount   INTEGER NOT NULL,
    remaining_amount INTEGER NOT NULL,
    expires_at       TIMESTAMPTZ NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT ck_user_credit_grants_amount
        CHECK (granted_amount > 0 AND remaining_amount >= 0 AND remaining_amount <= granted_amount)
);
```

- `user_credit_transactions.transaction_type` 约束增加 `credit_expired`（负数流水，表示过期作废）。
- 索引：`(user_id, expires_at, id) WHERE remaining_amount > 0` 供 FIFO 扣减；`(expires_at) WHERE remaining_amount > 0` 供过期扫描。

## 方案比较（Alternatives）

| 方案 | 评价 |
| --- | --- |
| 只给签到流水加 `expires_at`，定时任务"扣到余额为 0 为止" | 无需新表，但账户没有"这笔还剩多少"，无法知道该作废多少；用户当天已把签到积分花掉时，回扣会错扣永久积分；不采用。 |
| 全量批次台账（所有来源发放都建批次，退款精确回滚到被扣批次） | 账目最精确、最可扩展，但要改 6 个发放点、额外维护"扣费命中批次"使用台账，并回填历史余额；本期只有签到会过期，收益不抵复杂度；不采用，保留为后续扩展路径（届时给对应来源的发放补写批次即可）。 |
| 只对会过期的发放建批次 + 先到期先扣 | 表结构与改动面收敛在签到发放与扣减原语上，余额语义与读路径不变、无需回填；采用。 |

## 原因（Rationale）

- 只有签到会过期，批次台账只为"会过期的额度"服务，避免为永久积分维护一套永远用不到的台账。
- FIFO 扣费保证用户优先消耗最快到期的额度，签到积分不会被永久积分挤掉，是用户利益最大化的顺序。
- 余额继续作为权威读值，前端、用户列表、积分统计零改动，回归面小。
- 退款发新批次的语义在现模型下等价于"直接累加余额"，不需要任何额外机制。

## 影响（Consequences）

### 正面影响

- 签到积分真正实现"当天有效"，过期自动作废并在积分明细留痕。
- 前端余额、积分统计、管理端用户列表、卡密/邀请/初始发放链路零改动。
- 升级不需要数据回填，`credit_balance` 语义不变。
- 后续要给其他来源加有效期时，只需要该来源发放时补写一条批次，表结构不变。

### 负面影响

- 扣减侧需要改造：`CreditService.chargeTask`、`chargeOperation`、`adjustUserCredits`（负数分支）从 `changeBalance` 换成新原语 `consumeCredits`；签到发放改为"批次 + 余额 + 流水"三写。
- 每次扣费增加一次批次查询与若干次批次更新。
- 积分明细新增「积分过期」类型。

### 风险

- 并发扣费必须持有批次行锁（`SELECT ... FOR UPDATE`），否则可能超扣批次或余额。
- 过期清理与用户扣费会竞争同一批批次行，两者都必须先锁行再改。
- 有效期按签到时刻 + 24 小时计算，不再对齐午夜；定时任务每小时兜底，展示余额最坏滞后 1 小时（扣费路径的惰性过期会即时纠正可用额度）。
- 时区必须统一 `Asia/Shanghai`，否则签到日期与过期判定会出现偏差。
- 双写不一致风险：需要提供对账口径（`SUM(remaining_amount) <= credit_balance`）便于排查。

## 后续行动（Action Items）

1. 迁移 V31：建 `user_credit_grants`，`user_credit_transactions.transaction_type` 增加 `credit_expired`，并同步 `docs-api/backend-database.md`。
2. `CreditRepository` 新增原语：`createExpiringGrant`、`listGrantRowsForUpdate`、`consumeGrant`、`clearGrant`、`listExpiredGrantUserIds`。
3. 新增 `CreditGrantService`：`grantExpiringCredits`、`consumeCredits`（惰性过期 + FIFO 扣减）、`expireAll`。
4. `CheckInService.grantCredits` 改为写批次（`expires_at` = 签到时刻 + 24 小时）+ 加余额 + 写 `daily_check_in` 流水。
5. `CreditService` 的 `chargeTask`、`chargeOperation`、`adjustUserCredits`（扣减分支）接入 `consumeCredits`；发放类调用点保持不变。
6. 新增 `CreditExpiryScheduler`（每小时第 5 分钟），按用户汇总写 `credit_expired` 流水并推送余额变更事件。
7. 前端：`ServerCreditTransactionType` / `ServerCreditSource` / 来源筛选 / 类型文案 / 图标接入 `credit_expired`；签到页与后台「签到积分」Tab 文案改为"签到积分自签到起 24 小时内有效，过期自动作废"。
8. 补充并发扣费、惰性过期、定时清理与余额对账的服务端测试。
