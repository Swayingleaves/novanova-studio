# ADR-001: OAuth2 邀请上下文传递

## 状态

Accepted

## 日期

2026-09-09

## 背景（Context）

邀请注册需要在第三方 OAuth2 授权跳转前验证邀请码，并在用户离开本站、完成授权回调后可靠识别邀请人。邀请人标识属于服务端业务数据，不应直接放入可篡改的回调查询参数。

## 问题（Problem）

需要在跨站 OAuth2 跳转期间安全保存邀请关系，同时限制数据暴露、重放窗口和错误降级，且兼容现有 WebFlux OAuth2 会话流程。

## 决策（Decision）

使用 Redis 保存十分钟有效的一次性邀请上下文，内容仅包含登录渠道与邀请人用户 ID。浏览器通过路径限制为 `/api/v1/auth/oauth`、`HttpOnly`、`SameSite=Lax` 的 WebSession Cookie 间接持有随机上下文标识。OAuth2 成功回调使用 Redis `GETDEL` 原子消费上下文；上下文过期、重复使用或渠道不匹配时明确终止登录流程。

## 方案比较（Alternatives）

- 将邀请码或邀请人 ID 放入回调 URL：实现简单，但参数可见且可篡改，需要额外签名与重放防护。
- 仅保存在进程内 WebSession：可复用现有流程，但无法独立控制邀请数据的有效期和一次性消费。
- Redis 服务端上下文加受限 Cookie：支持一次性消费和明确有效期，且浏览器无法读取邀请数据。

## 原因（Rationale）

项目已经使用 Redis 和 WebFlux WebSession，无需引入新基础设施；一次性原子消费可以避免重复 OAuth2 回调重复携带邀请关系，十分钟有效期足以完成常规授权并限制风险窗口。

## 影响（Consequences）

### 正面影响

- 邀请人标识不经过浏览器明文传递，无法由前端直接篡改。
- 邀请数据集中存储在 Redis，并能明确识别过期和重复回调；会话路由能力与现有 OAuth2 WebSession 部署约束一致。
- Cookie 仅在 OAuth2 路径发送，降低暴露范围。

### 负面影响

- OAuth2 邀请登录依赖 Redis 可用性。
- 用户授权超过十分钟后必须从邀请链接重新发起。

### 风险

- Redis 数据提前丢失会导致本次邀请授权失败，但不会静默按无邀请登录。
- 本地 HTTP 开发环境不能强制 Cookie 的 `Secure` 属性，生产环境应由 HTTPS 和边缘层保证传输安全。

## 后续行动（Action Items）

- 监控 OAuth2 邀请上下文过期与无效错误数量。
- 部署环境统一启用 HTTPS，并验证反向代理保留 Cookie 属性。
