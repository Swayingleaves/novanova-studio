# 📚 小说导入与智能改编版本路线图

## 🎯 文档目的与当前基线

本文说明 NovaNova Studio 在原文导入之后，如何逐步形成**可编辑的故事知识库**，再把它用于剧本与漫剧生产。本文是产品路线图；各版的接口、数据迁移和技术实现以实施前的专项设计为准。

| 版本 | 定位 | 当前状态 |
| --- | --- | --- |
| 第一版 | 上传剧本或小说，保留原文件，解析章节、场景与文本片段，支持人工校对结构 | **已完成** |
| 第二版 | 从原文建立可编辑、可追溯的故事知识库 | **已完成** |
| 最终版 | 从故事知识库贯通改编剧本与漫剧生产 | **代码实施完成，待验收** |

这里的 **Story Bible（故事知识库）** 是供创作者查看、查询和修改的故事设定与事实集合；原文证据、人工确认结果和改编成果需要保持关联。三个版本在**同一个创作项目**中逐步增加能力，不另外创建一套剧本或漫剧项目。

相关现有文档：[剧本创作功能规格](./剧本创作功能规格.md)、[漫剧创作功能规格](./漫剧创作功能规格.md)、[剧本创作与漫剧创作功能总览](./剧本与漫剧创作功能总览.md)。这些文档中的“当前状态”是各自编写时的历史记录；判断某项功能是否可用，应以对应版本的实际实施与验收结果为准。

## 🧠 第二版：可编辑、可追溯的故事知识库

### 🎯 目标与用户流程

用户在第一版校对原文结构后，启动分段分析，逐步得到**人物、别名、人物关系、地点、事件、故事线和时间线**。用户能够从结论跳回原文、修正错误，并决定哪些内容成为后续改编的可信依据。

```mermaid
flowchart LR
    A[已导入并校对的原文] --> B[分段分析]
    B --> C[跨章节归并与冲突提示]
    C --> D[故事知识库]
    D --> E[查看证据与人工确认]
    E --> F[供改编使用的故事事实]
```

### 🧩 主要能力

| 能力 | 用户可见结果 |
| --- | --- |
| 人物与别名 | 同一人物的不同称呼归并展示；用户可合并、拆分或修改人物 |
| 关系与事件 | 查看关系如何随剧情变化，以及事件的参与者、地点、前后顺序和所属故事线 |
| 时间线与地点 | 同时查看原文叙事顺序和故事发生顺序；无法确定的时间保留为待确认信息 |
| 原文追溯 | 重要事实与关系可定位到来源章节、场景和原文片段，展示分析置信度及待确认状态 |
| 人工校对 | 用户可修改、删除、补充并确认分析结果；重新分析相关片段时保留人工修改 |
| 长任务恢复 | 可查看阶段进度、失败原因并重试；中断后从已完成的工作继续，不重复创建事实 |

### 📌 版本边界与验收里程碑

- 第二版交付**故事事实的抽取、查询、证据查看和人工确认**，止于可编辑的 Story Bible；不自动生成完整分集剧本、分镜或付费媒体。
- 用一部超过 100 万字的真实长篇小说完成全书分析，验证人物别名归并、关键事件与关系、时间线和原文定位；对遗漏与误判提供人工修正入口。
- 模拟任务中断、失败重试与人工修改后局部重新分析，确认任务能继续、事实不重复，且人工确认内容不被自动覆盖。
- 用户能从故事知识库选取已确认的设定与事实，作为最终版改编的输入。

## 🎬 最终版：完整改编与漫剧生产

### 🎯 目标与用户流程

用户选择改编形式、目标集数、单集时长、节奏与改编程度，在**已确认的故事知识库**基础上依次审阅大纲、分集规划、剧本和分镜，再使用现有剧本创作与漫剧创作能力组织视觉资产和媒体生产。

```mermaid
flowchart LR
    A[已确认的故事知识库] --> B[故事大纲]
    B --> C[分集规划]
    C --> D[分集与场次剧本]
    D --> E[镜头清单与分镜]
    E --> F[人物 场景 道具资产]
    F --> G[图片 声音 视频制作]
    G --> H[成片编排]
```

### 🧩 主要能力

| 能力 | 用户可见结果 |
| --- | --- |
| 故事大纲与分集 | 按故事线、事件和人物成长组织大纲与集数；每集明确核心事件、冲突、节奏和结尾悬念，不机械对应原文章节 |
| 结构化剧本 | 基于已确认的规划生成和编辑分集、场次、动作、对白与旁白，并保留其原文与故事事实来源 |
| 分镜与资产 | 将剧本场次转为可编辑镜头；关联共享项目中的人物、地点、道具设定及对应视觉资产 |
| 媒体生产 | 在漫剧工作台中使用现有画布、分镜和生成能力制作图片、声音与视频，并编排成片 |
| 变更影响 | 上游故事事实或剧本改变时，标记受影响的分集、镜头与资产；保留已完成内容，由用户选择更新范围 |
| 一致性检查 | 提示人物设定、关系、时间、地点与剧情因果中可能冲突的内容，并提供来源供人工判断 |

### 📌 版本边界与验收里程碑

- 复用同一剧本项目和现有漫剧生产数据，不复制正式剧本；已有人工作品、分镜和生成资产不因上游修改被自动覆盖。
- 所有可能扣费的图片、声音、视频生成由用户明确发起；影响提示本身不触发生成。
- 以真实长篇小说完成“原文 → 故事知识库 → 大纲 → 分集 → 剧本 → 分镜 → 资产与媒体 → 成片编排”的演示，并逐阶段确认产物可编辑、可追溯。
- 修改一项上游人物或事件后，能够查看受影响内容并选择局部更新；未选择更新的人工修改和已生成资产保持原状。

### ✅ 最终版已确认实施规则

- 改编生成只使用用户选择且已经确认的故事事实；未确认或未选中的事实不得作为生成依据。
- 长篇内容采用“全局规划、逐集生成”：先生成全局大纲，再按集生成分集规划和场次剧本，避免一次请求处理整本书。
- 大纲、分集规划和单集剧本分别生成可编辑草稿；用户逐阶段审阅后，只将选中的目标局部写入同一个剧本项目。
- 未选中的已有人工内容不得覆盖或删除；草稿中的新增目标可以追加，并重新生成连续的集号、场次号和排序。
- 允许新增原文没有的情节、人物或对白，但必须标记为“改编创作”，不得伪装成已确认故事事实；与事实冲突时提示用户审阅。
- 上游故事事实变化只生成影响提示并提供可选更新范围，不自动覆盖剧本、分镜、资产或媒体。
- 一致性检查先提供免费的规则检查；深入模型检查只有在用户明确确认费用后才执行。
- 图片、声音和视频生成仍由用户主动发起，改编草稿、影响提示和一致性检查不得隐式触发媒体生成。

## ⚙️ 技术边界

路线图优先复用项目现有的 **Spring Boot、PostgreSQL、Redis、云对象存储、剧本工作台和漫剧生产能力**。Neo4j（图数据库）与 pgvector（PostgreSQL 向量检索扩展）只在实际关系查询或语义检索效果表明有必要时单独评估，**不是第二版或最终版的交付前提**。
